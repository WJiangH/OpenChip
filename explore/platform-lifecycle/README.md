# OpenChip：NPU SoC 与 agent 开发生命周期草案

状态：讨论稿；不替代已接受的 ADR，不授权下游按新接口实现。
日期：2026-09-05
角色：chief-architect
检查基线：`0b5d9bb`。本文件是范围与流程设计，不是已实现能力报告。

## 1. 目标与已确认方向

- 产品目标：一款有实际应用价值、以 NPU 为核心的完整 SoC；先整芯片仿真执行真实程序，再推进 FPGA。
- 平台目标：agent 工作流适应芯片架构，覆盖持续开发中的增加、修改、删除和替换 block。
- 系统主互连优先评估 AXI；安全域评估 Caliptra。版本、具体集成模式和资源预算尚未冻结。
- 后续引入可执行系统模型，以及 vendor IP 的模型替身和自研实现替换流程。
- “功能强大”必须转化为工作负载、数值精度、延迟、持续吞吐、带宽、容量及功耗/面积预算；当前没有新的获批数值目标。

两条独立验收线：芯片是否正确且满足目标；协作流程是否可靠、成本可接受。芯片跑通不能单独证明多 agent 更高效。

## 2. 架构与平台规则的分层

| 层次 | 内容 | 变更方式 |
|---|---|---|
| 平台不变量 | 规格来源、设计/DV 独立、证据可复现、角色边界、变更可追溯、不得弱化 gate | 维护者审阅的平台规则变更 |
| 项目配置 | ISA、总线版本、互连拓扑、时钟/复位、电源域、工艺、IP、工具链和目标板 | 架构决策 + 受影响交付物清单 |
| block 合同 | 功能、寄存器、协议、数值行为、错误处理、时序义务、参数 | 有版本的规格变更 |
| 实现适配 | 自研 RTL、上游 IP、模型、FPGA 存储器与 ASIC 宏的适配 | 同一合同下分别验证的实现 |

AXI、Wishbone、某种 CPU 或 EDA 工具不应成为平台宪法的不变量；项目可以选择它们并承担明确的验证义务。架构自由不等于免除协议细节或资源约束。

现有 `AGENTS.md`/ADR-0001 将 Wishbone 和工具支持的 HDL 子集写成全局约定。拟通过单独规则变更拆分；本草案不修改这些约定，也不放宽现有 gate。第三方 IP 的语言和工具需求先独立验证，再裁决工具链适配方案。

## 3. 第一款芯片的完整功能域

| 功能域 | 需要明确的职责 | 当前定位 |
|---|---|---|
| 主机控制 | CPU、启动 ROM、固件、异常、中断、调试 | 核型待重新评估；保留既有候选 |
| NPU | 算子集合、量化算术、指令/描述符、调度、局部存储 | 主体自研方向；阵列和规模由新工作负载研究决定 |
| 数据搬运与存储 | DMA、片上 SRAM、外部存储控制器、仲裁和带宽预算 | 整芯片关键路径；必须从最初架构纳入 |
| 系统互连 | AXI 主干、控制接口、流接口、地址和访问权限 | 候选；不能只冻结“使用 AXI”四个字 |
| 安全与启动控制 | 信任边界、固件授权、度量、恢复、调试权限、密钥生命周期 | Caliptra 候选；接入模式尚未决定 |
| 系统服务 | UART、GPIO、定时器、watchdog、复位和时钟管理 | 按应用和启动需求配置 |
| 实现平台 | 仿真外设、FPGA wrapper、ASIC 存储器/PHY/pad 适配 | 核心软件合同尽量一致，平台差异显式记录 |

完整架构不要求所有 block 第一批同时开工。先做贯穿各必要层的可运行路径，再逐步增加计算能力；最终性能目标不以初始启动 demo 代替。

CPU 和安全管理 MCU 的职责必须区分。Caliptra 需要何种主机、互连和存储资源，须按选定 release 核实，不预设“接一个 mailbox 就完成安全启动”。

## 4. 增加、修改、删除、替换 block 的统一变更闭环

每次变更都有独立 change ID，并记录：原因、基线、目标合同版本、依赖者、责任角色、迁移方法、回退方法、需重跑的 gate 和接受结果。

| 操作 | 必须处理的影响 | 额外验收 |
|---|---|---|
| 增加 | 规格、地址、中断、复位、电源、互连、软件驱动、模型、资源预算 | 新功能及其与现有系统并发运行；原有程序回归 |
| 修改 | 合同/实现差异、ABI、时序、性能、依赖 block、测试计划 | 新要求覆盖；旧行为保留或显式迁移；受影响证据失效并重跑 |
| 删除 | 上游请求者、驱动、地址空洞、中断、模型、构建清单、物理约束 | 无悬空引用；访问已删除资源的行为明确；剩余系统回归 |
| 替换 | vendor 与自研实现的能力差异、接口、时序、许可来源和软件兼容 | 独立合同测试、差分/一致性验证、系统回归、适用实现 gate |

删除功能相关测试只能发生在功能退役已获批准、替代验收已定义之后；不能用删 block/删测试掩盖原先失败。缺失 gate 标为未实现或阻塞，不能作为通过。

流程：需求/变更 → 架构裁决与版本化合同 → 影响分析 → RTL、DV、formal、软件、模型等角色独立执行 → 子系统集成 → 整芯片回归 → 实现检查 → 独立审阅和证据归档。

拟建立机器可读 block 清单：ID、合同版本、实现来源/固定版本、接口参数、地址、中断、时钟/复位/电源域、依赖、owner、测试和构建入口。它服务于影响分析和一致性检查；不得用自动生成的清单替代架构判断，也不自动授权删除。

## 5. test plan 的完整性合同

验证架构师独立于 RTL 作者制定分层 test plan。每条要求映射到：测试/属性 ID、激励、独立预期来源、可观察结果、通过条件、覆盖目标、执行层次、适用配置和责任人。

| 层次 | 必须纳入计划的场景 |
|---|---|
| block | 正常、边界、非法输入、复位中断操作、数值溢出/舍入/饱和、参数组合 |
| 协议与子系统 | 反压、并发、仲裁、事务顺序、突发边界、错误响应、超时、数据完整性 |
| 整芯片 | 冷/热启动、真实固件、DMA+NPU+CPU 并发、中断、复位恢复、外存延迟 |
| 安全 | 未授权访问、篡改固件、适用的版本回退限制、调试权限、失败后的隔离/恢复 |
| 软件与算子 | 驱动/API、参考数值、算子组合、完整网络、精度与可复现输入 |
| 性能 | 实际工作负载的计算/搬运分解、带宽竞争、长时间持续吞吐和内存容量边界 |
| 实现 | 综合、时序、CDC/RDC、适用低功耗/DFT 检查、网表回归、物理检查 |

“完整”指范围内的要求都有验证义务和状态，不意味着穷尽所有可能输入。代码覆盖率、功能覆盖率、要求覆盖率分别报告；formal 标明假设、边界和证明深度，不能用有限证明宣称全系统无错。

数字功能仿真不能证明真实熵源、OTP 保密、抗物理攻击或硅上可靠性。FPGA 功能运行也不能代替 ASIC 电气与物理签核。

## 6. 角色与目前缺口

沿用现有九角色，保持 RTL/DV/模型的独立来源。一个角色可以有多个 block owner；不要求每个任务都启动九个 agent。编排器按依赖和资源预算安排工作。

| 工作项 | 责任方案 |
|---|---|
| 产品与性能架构、IP 选择、合同裁决 | chief-architect；先做工作负载研究和设计空间分析 |
| test plan、参考模型、验证基础设施 | verif-architect |
| block RTL / 子系统与顶层连接 RTL | rtl-engineer 分别持有对应模块；顶层必须有明确作者 |
| block/子系统/SoC 测试、缺陷复现 | dv-engineer；不修改被测 RTL |
| 属性与协议证明 | formal-engineer |
| 启动、驱动、运行时和应用 | sw-engineer；编译器/算子映射工作量单独规划 |
| 可执行系统模型与性能校准 | model-engineer；不从 RTL 或 DV golden 复制预期 |
| 综合、布局布线、时序及物理适配 | backend-engineer |
| 审阅、证据、gate 完整性 | integrator；不编写顶层产品 RTL |
| 共享构建/CI/回归调度与资源管理 | orchestrator 所有的 flow 工作项 |

需补充责任合同的领域：DFT/ATPG/MBIST、安全架构与验证、CDC/RDC 和低功耗、FPGA/emulation、封装与板级、实验室 bring-up、硅后验证、量产测试和 ECO。先明确任务、所需工具与证据，再决定新增专门角色还是扩展现有角色；本文件不直接更改 skill。

“覆盖真实开发场景”分为：流程已定义、工具已接通、代表性案例已跑通三个状态。模拟/混合信号、工艺相关宏、量产和物理安全等领域可以先定义交接与验证边界；未执行过不能计为平台已验证能力。

## 7. digital twin 与 vendor IP 替换

为了避免同名不同义，暂分为三个交付层次：

1. 功能虚拟平台：执行真实软件，复现合同定义的寄存器、事务、数值和错误行为。
2. 校准性能模型：在功能基础上增加有来源的延迟/带宽/竞争模型；标出校准工作负载和参数区间，外推单独标识。
3. RTL/FPGA/硅关联模型：比较同一输入、软件版本与观察量，跟踪偏差和适用范围。

模型替身可以替换仿真环境中的 vendor IP，但不因此成为可综合硬件。最终硬件替换需要独立的 RTL 交付及相应功能、时序、面积/功耗、软件和物理验证。

替换顺序候选：合法取得的公开合同/接口资料 → 模型替身 → 独立协议与功能一致性测试 → 自研 RTL → 与参考实现可观察行为比较 → SoC 回归 → FPGA/ASIC 适用验证。

区分“软件可见功能兼容”“时序/协议兼容”“完整等价”。vendor 的未公开行为或不可取得参考不能凭猜测补成合同；PHY、PLL、SRAM 等物理 IP 需要工艺/电气证据，数字模型只能支持限定的仿真用途。

## 8. 分阶段证明芯片与工作流

| 阶段 | 芯片验收 | 工作流验收 |
|---|---|---|
| P0：范围与合同 | 新工作负载、候选架构、预算、IP/工具可运行性探针 | block 清单、change order、角色与 gate 责任明确 |
| P1：整芯片最小运行路径 | 冷启动 → 实际固件 → 搬运非零输入 → NPU → 可核对输出；无内部状态注入替代软件接口 | 首次跨角色交付、缺陷退回、独立系统验收 |
| P2：计算与系统能力 | 选定网络/算子、明确精度与性能目标、竞争和异常用例 | 独立评估分支上各完成至少一次 add/modify/delete；比较修改前后证据 |
| P3：FPGA | 同一软件合同和应用运行；记录平台差异、资源与性能 | 平台适配变更的影响分析、回归与交接 |
| P4：模型与替换 | 模型执行同一软件；选择一个可验证 IP 完成替身与实现替换 | replace 的兼容性、差分和系统验收 |
| P5：ASIC 与硅后 | 工艺/宏/DFT/物理签核、封装板级和硅后目标另行冻结 | 逐项建立真实工具与实物证据；不能继承 blink 的成功为 SoC 签核 |

安全域在 P0 定义信任边界；选型探针可与功能路径研究并行。安全启动作为独立集成关卡，确定落点后更新计划，不能默认为 P1 已有。

协作评估记录：首次交接通过率、规格返工次数、缺陷发现阶段、回归逃逸、人工介入次数/时长、墙钟时间、模型与工具资源成本、干净环境复现成功率。高缺陷数可能来自低质量规格，不能直接奖励“找 bug 数量”。

要声称协作更高效，需匹配任务、验收标准与工具条件的基线，并重复样本；在单一成功案例上只报告可行性。比较不同编排方式时仍保留 RTL/DV 独立，不能让同一作者自验来省成本。
