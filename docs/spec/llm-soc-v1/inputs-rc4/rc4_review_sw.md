## Findings

### SW-RC4-01 — P2: SYS-08's newly hardware-enforced CSR-write rejections are unrecoverable/unobservable by firmware, and the text doesn't say so in one place

Location: `system.md:65` (SYS-08, rc4 sentences: *"WO command registers (RESULT_COMMIT, NPU SUBMIT, NPU CLEAR) accept exactly the written word value 1: any other written word, including 0, returns SLVERR and has no effect... Value ranges stated in the sys and UART register rows are hardware-enforced: a BOOT_STAGE write with value above 4 and a DIVISOR write with field value below 2 return SLVERR and change nothing"*), cross-read with `system.md:61` (SYS-07: *"The adapter must not return a successful native completion for the failed operation"*), `system.md:95` (SYS-13: *"a failing request receives no mem_ready (SYS-07)"*) and `system.md:93` (SYS-12: `cpu_local_rst_n = rst_n & boot_delay_done & !FATAL`).

Before rc4, a stray firmware write of `BOOT_STAGE=5` or `DIVISOR=1` (both class F-07/uart-01, "provisional (unenforced)") was a harmless OKAY no-op; a stray `SUBMIT`/`CLEAR` write of 0 was already SLVERR only at `npu_csr` (F-05's "npu_csr provisional confirmed" half) but a stray `RESULT_COMMIT` write of 0 was OKAY. rc4 makes every one of these SLVERR. Per SYS-07/SYS-13, the native bridge never asserts `mem_ready` for a failing store, so the PicoRV32 core's store instruction never retires; per SYS-12 the CPU is simultaneously placed in local reset. The result is indistinguishable, from firmware's point of view, from an unconditional hang at that exact instruction: there is no trap, no returned error code, no subsequent instruction execution in which firmware could branch on a "write rejected" outcome — RESULT_COMMIT can never be reached to report a code, and the sys `FATAL`/`FAULT_ADDR` registers this produces are readable only by an external DV/waveform observer (there is no second bus initiator in this system), never by the halted CPU itself. This is architecturally consistent with the pre-existing rc3 rule that *any* CSR SLVERR to the CPU is fatal (SYS-07 predates rc4), but rc4 measurably widens which ordinary-looking, single-bit-off values (BOOT_STAGE=5 instead of 4, DIVISOR=1 instead of 2, RESULT_COMMIT=1 written twice) now fall into that silent-hang class instead of a benign no-op. The change order's own disposition table only says "SW: none" for these rows (asserting current firmware never hits the path) without stating the consequence explicitly for a future firmware author.

Problem: a reader implementing new firmware logic against SYS-08 alone could reasonably code a "check BRESP, log an error, keep going" retry path around one of these WO/range-checked writes, which is unimplementable — the instruction never completes to be checked. This does not block implementing the current B1 driver from text (NPU-08 and the boot sequence as specified never issue such a write — see SW-RC4-checked list below), but it is a real ABI-consequence gap for anyone extending the driver.

Proposed text: append to SYS-08 (exact sentence given in the decision line above).

### SW-RC4-02 — P3 (editorial): LAST_CYCLES stability under a busy/terminal-uncleared SUBMIT rejection is correct only by cross-reference, not stated

Location: `npu.md:35,37` (NPU-04 row and rc4 LAST_CYCLES paragraph: *"A malformed idle SUBMIT rejected at the CSR layer (NPU-05) produces no dispatch and does not modify LAST_CYCLES (rc4)"*) vs `npu.md:39` (NPU-05: *"SUBMIT while BUSY or terminal status uncleared shall return SLVERR and leave the active command, status, tag and output unchanged"* — LAST_CYCLES is not named in this list).

rc4 explicitly closes the "malformed idle SUBMIT" case for LAST_CYCLES (this is the ISSUE-npu_ctl-02/F-06 ruling) but the other SUBMIT-rejection case in the same requirement — SUBMIT while BUSY or terminal status uncleared — is a plain bus-level SLVERR whose "no state change" guarantee for LAST_CYCLES follows only from the general SYS-08 sentence ("Other sizes, strobes, offsets or writes to RO registers return SLVERR, reads return zero on error and no state changes") plus the absence of LAST_CYCLES from NPU-05's explicit unchanged-list. The answer is unambiguous once both rules are combined, so this does not block a driver implementation (the driver never depends on LAST_CYCLES after a rejected SUBMIT — NPU-08 only reads LAST_CYCLES, if at all, after a successful terminal), but it is one inference hop that the rc4 edit for the sibling case (malformed idle SUBMIT) did not need.

Proposed text: append to the LAST_CYCLES paragraph (exact sentence given in the decision line above).

## Checked, no finding

- **SYS-05/SYS-06 taxonomy is complete and each failure has exactly one code.** `system.md:59` enumerates every SYS-05 (`system.md:57`) failure predicate into exactly one of 0xB001 (magic, ABI, byte_length∉[1,0x30000], load≠0x10000000, entry≠0x10000000, any nonzero word 8..15), 0xB002 (CRC comparison only) or 0xB003 (BSS start/alignment/length/end, payload-source-within-boot-image, 64-bit wraparound). No SYS-05 predicate is left unassigned or dual-assigned. The reserved-words rule is unambiguous ("a nonzero reserved word is an invalid header, not don't-care"), matching the already-`spec-clear` disposition of ISSUE-sw_b1-01.
- **Check order matches "validate before copy" and CRC-over-destination.** `system.md:59`'s new sentence "Checks are applied in the order header, bounds, copy, CRC" is verbatim consistent with `system.md:57`'s existing "ROM validates header and bounds before copy, copies via CPU AXI load/store, validates CRC over destination bytes" — CRC is explicitly over destination bytes (post-copy, in SRAM), never source. Both sentences agree; no reordering ambiguity.
- **Wraparound is scoped correctly.** Only the bounds-class checks (BSS arithmetic, payload-region fit) perform address addition that can wrap; byte_length/load/entry are plain constant comparisons with no wraparound exposure, consistent with 0xB003 being the sole bucket that names "any 64-bit wraparound" (`system.md:59`).
- **SYS-08 WO write-1-only and BOOT_STAGE/DIVISOR range enforcement do not reject any write the text requires firmware to make.** NPU-08's driver sequence (`npu.md:47`, "CLEAR previous terminal state; ... SUBMIT; wait on STATUS or IRQ ...") never writes a value other than 1 to CLEAR/SUBMIT/RESULT_COMMIT. The boot sequence's only stated BOOT_STAGE writes are 2 (ROM, `system.md:59` context) and 3 (B1, per CHANGE_ORDER_rc4.md's F-07 row: "rom writes 2, b1 writes 3"), both inside 0..4. No requirement text directs firmware to write DIVISOR at all (UART row default `reset16` is presumably retained); the range 2..65535 (`system.md:88`) is therefore never legitimately violated by any driver sequence described in the contract. (This traces only the requirement text; the actual `sw/rom_main.c`/`sw/b1` source is out of this role's read scope and was not inspected.)
- **`contract.json` `csr_registers` matches the prose tables exactly, byte for byte, after rc4.** Verified programmatically: `sys` block (ID/VERSION/BOOT_STAGE/FATAL/FAULT_ADDR/RESULT_CODE/RESULT_COMMIT/CYCLE_LO/CYCLE_HI/BUILD_CONFIG), `npu_csr` block (all 17 registers 0x00..0x40 including the rc4-touched SUBMIT/CLEAR/LAST_CYCLES), `irq` block (PENDING/ENABLE/ACTIVE, bits 0/1/2) and `uart` block (TX_DATA/STATUS/DIVISOR) all have offsets, `access`, `reset` and field `msb`/`lsb` identical to `system.md`/`npu.md` §2/§3 rows. `address_regions` (14 rows) is unchanged from the rc3 table in `system.md` §2. `irqs` (IRQ4/5/6) unchanged. rc4's new value-range/WO-exactly-1 rules live in prose only (no numeric-range field was added to `csr_registers`), which is the existing, already-established house convention ("contract.json wins for names/widths; prose wins for semantics" — cited in ISSUE-npu_ctl-01's disposition) rather than a new omission.
- **`workload.md` is untouched by rc4** (no hunk in the diff; file header still reads "Version 1.0-rc3"), consistent with every workload-adjacent CHANGE_ORDER_rc4.md row showing "SW: none" and with rc4's own claim of no numeric-format/ABI-major change. The rc2-review's three open findings (SW-RC2-01/02/03, SiLU order / CRC-coverage / data_bytes definition) are outside rc4's ruled-issue set (workload.md was not touched by any of the 27 issues) and remain wherever rc2's review left them — not reopened or worsened here.
- **NPU-09/dma_terminal/dot_lifecycle changes are internal-partition-only and do not change the NPU-08 driver sequence.** `npu.md:56` (NPU-09) and the NPU-06 rc4 addition (`npu.md:41`, "a result still held in npu_dot or operands still held in npu_local are not awaited, because the NPU-09 flush and dispatch re-arm discard them before the next command can start") only pin *when internally* BUSY/DONE/ERROR/ERROR_CODE/tag become externally visible relative to internal dot/local residue draining; the CSR-visible contract itself — STATUS bits, IRQ level expressions, CLEAR-then-SUBMIT sequencing, COMPLETED_TAG latch timing relative to DONE/ERROR — is unchanged. `npu.md:47` (NPU-08) is untouched text. No back-to-back CLEAR/SUBMIT timing assumption in NPU-08 depends on cycle-exact internal drain, so the driver sequence in the spec is unaffected.

- **No scope creep against software.** Every rc4 row whose "Affected artifacts" column lists an SW file states "SW: none" except the two sw_b1 rows, which are `spec-clear`/`spec-gap` confirmations of the *already-implemented* rc3 firmware behavior (no code change requested). The metadata-only rows (ISSUE-cpu_bridge-02, ISSUE-mem-01, ISSUE-npu_dma-03) touch only `contract.json` owner lists/purposes and `traceability.md`, none of which are read by firmware. F-02/F-03/F-08/F-09 (the genuine SW-owned defects/ledger items) are explicitly left to the SW author or the orchestrator in CHANGE_ORDER_rc4.md's "Not ruled here" section, correctly kept out of this spec change order per Iron Rule 1 (spec text vs. implementation-level bug).

Friction:
- The rc4 taxonomy/enforcement text is spread across SYS-07/SYS-08/SYS-12/SYS-13 for a single observable consequence (silent unrecoverable hang on CSR-write rejection); assembling it required cross-reading four requirements plus contract.json `protocols.native`/`stop_new_transactions`.
- `inputs-rc4/integrator-review-01.md` is large (409 lines) but is the only place several rc4 rulings' underlying RTL-author disagreement (F-01/F-04/F-05/F-06/F-07) is explained; CHANGE_ORDER_rc4.md's ruling rows are terse enough that the "why" required reading the linked ISSUE-*.md files individually.
- `workload.md` still carries a "Version 1.0-rc3" self-declared header while every other file in the package was bumped to "Version 1.0-rc4"; harmless here since the file is untouched, but worth a house-rule note (bump the version string only in files a change order actually edits, or bump it everywhere for round consistency) to avoid a future reviewer mistaking an unbumped header for a missed edit.
