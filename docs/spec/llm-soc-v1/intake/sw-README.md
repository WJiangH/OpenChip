## Executed workload and numerical meaning

The exact source text in `driver.c` encodes to 41 IDs using upstream tokenizer code and the matched tokenizer. The first 32 IDs including BOS are used as the prompt; it ends in the space after “play”. IDs and readable text are in each raw log and JSON. Greedy argmax chooses the lowest ID in a tie, temperature zero, no RNG, no top-p, no EOS early stop. All 32 prompt tokens execute every layer sequentially (GEMV prefill, not an optimized GEMM prefill).

The final prefill logits select generated token 1. Sixteen decode forward calls consume generated tokens 1 through 16; decode calls 1 through 15 select tokens 2 through 16. The prediction from the final call is not emitted. This yields 16 generated tokens and a KV cache with all 48 consumed positions, without an off-by-one claim about prefill or cache population. Free-running FP32 and both quantized candidates produce `outside. One day, she went to the park`. Teacher-forced variants separately consume all 48 FP32 input IDs; their JSON `generated_ids` denotes the prediction at the corresponding boundary and must not be mistaken for the supplied teacher input sequence.

Every forward exports `logits[512], final-normalized-hidden[64], layer0..4 {new K[32], new V[32]}` as 896 little-endian float32 values. Append K/V rows per layer to reconstruct the complete cache at any position. `artifacts/*.inputs.i32` fixes each consumed token. `metrics.json` contains per-step and aggregate errors; aggregate KV error covers all 48 x 5 new K/V rows, each once. All outputs/weights are checked finite. Full FP32 checkpoints are byte-identical to a separately compiled wrapper including the unmodified pinned upstream `run.c`; the candidate derivative replaces only static matrix multiplication and optionally the embedding data.

## Candidate numeric rules (for architect decision)

- Static matrix W is compact row-major `[N,K]`. Quantize each row in contiguous K groups of 64, with the final group shortened. w2 has groups 64,64,44. The alternate perrow candidate has one group of K values. No group crosses a row. No packing/CSR/descriptor/DMA ABI is implied.
- For each W group, scale is FP32 `max(abs(W))/127`; an all-zero group uses scale 1 and values 0. A is dynamically quantized per input vector using the same K grouping. No calibration dataset is used.
- FP32 division then C `roundf` (nearest, half away from zero), clamp to [-127,127], signed INT8. Input NaN/Inf or invalid/nonpositive scale is rejected. This policy also rejects scale underflow to zero; no silent NaN/Inf substitution. Signed zero maps to zero.
- Each group computes the exact signed INT32 dot. With at most 64 elements the worst absolute sum is 1,032,256; perrow K=172 gives 2,774,188. No saturation is used or needed for these shapes. A more general K limit belongs in the architecture contract.
- CPU postscale is `sum += ((float)acc * weight_scale) * activation_scale`, FP32, groups ascending from zero, without fused multiply-add. Output remains FP32. Weight scales are `[N,ceil(K/64)]`; activation scales are `[ceil(K/64)]`; INT32 results may be written `[N,ceil(K/64)]` for CPU processing if architect chooses that layout.
- Shared embedding/head has one INT8 weight+scale representation. Host probe dequantizes the whole embedding for convenience and uses W8A8 for the tied classifier. A target can dequantize only the selected embedding row; that is a proposed optimization, not executed target firmware.
- RMSNorm gains, all other activations/residuals, Q/K RoPE, attention scores/softmax/value mixing, SwiGLU/SiLU, and KV remain FP32. Thus W8A8 describes static linear operations only, not the entire Transformer.

The NumPy analyzer independently reconstructs weight/activation quantization, every INT32 group dot, and FP32 postscale from raw traces: 1,728 matrix calls / 199,296 group dots for group64 and 168,576 for perrow. These are software reference checks, not hardware bit-accurate golden validation. The full nonlinear/attention implementation remains shared upstream C; the independent check does not independently reimplement those operators.

## Real upstream group64 incompatibility

The pinned `runq.c:145-170` quantizer uses `n / GS`; `runq.c:317-341` matrix loop only handles complete GS groups. `export.py:193-195` backs off based on model dim=64, not FFN width=172. Its flattened weight groups also cross w2 row boundaries. Do not use the unchanged group64 runtime as this model's numeric contract.

`tail_probe.py` runs the actual unmodified upstream quantizer and matmul on the first real-model layer-0 w2 input captured from the candidate full forward. All 44 tail inputs are nonzero; upstream leaves all 44 quantized tail values zero and their scale zero. Its result differs from FP32 by max 0.321632 / RMSE 0.107250, with a max 0.294181 contribution from the omitted FP32 tail alone. The total error also includes ordinary quantization and row/scale misalignment, so it is not attributed entirely to the tail. An independent reconstruction matches the upstream output exactly. This is an actual upstream operator reproduction, not a full upstream quantized-model run. Source snippets are retained verbatim in `vendor/` and summarized in `upstream_tail_metrics.json`.

## Architecture implications

Group64 with tail44 is viable as a small-model candidate, but a single prompt does not choose an optimum. Group64 fixed-trajectory logits max error 0.448473, RMSE 0.122319, relative L2 1.3115%; new K/V max 0.213680, RMSE 0.023627. Perrow logits max error 0.516534, RMSE 0.119836; K/V max 0.331371, RMSE 0.028463. Both share FP32 top1 for all 48 tested logits and all 16 emitted tokens. No perplexity, representative prompt suite, or quality threshold was evaluated. Group64 has smaller maximum reduction width and lower KV error here, while perrow has less scale/writeback data and slightly lower logits RMSE here.

For each layer, static NPU-candidate matrices `[N,K]` are q `[64,64]`, k/v `[32,64]`, o `[64,64]`, gate/up `[172,64]`, down `[64,172]`; final head `[512,64]`. All 36 static linears per token execute the candidate INT8 path, 259,328 integer MAC/token, 12,447,744 over 48 forwards. Attention is CPU FP32 in this probe: 640*(position+1) MAC/forward, 752,640 over 48 forwards. CPU additionally needs memory copies, max/abs, float quantization divisions/rounding, group postscales, RMSNorm (sum/sqrt/div), RoPE (pow/sin/cos), exp-based softmax and SiLU, residual/product, tokenizer, argmax, and KV indexing. On RV32IM those FP32/transcendental operations require actual software-float/libm support, linking, and timing; host success does not establish those costs or availability.

`metrics.json` contains exact byte definitions. Group64 model payload is 278,752 B: 259,328 INT8 matrix bytes + 16,608 FP32 scale bytes + 2,816 FP32 norm bytes. FP32 KV costs 1,280 B/position: 61,440 B at 48 used positions, versus 655,360 B reserved by the host's 512-position runtime. Host non-KV activation reservation is 20,832 B. A 48-context allocation would use 5,984 B, but was not instantiated in this host runtime. Whole embedding dequantization is 131,072 B host-only overhead; selected row scratch could be 256 B. All group results written once require 16,608 B/token group64 or 14,048 B/token perrow, before command/scale/activation/weight traffic. Tile size, row stride/tail, output layout and ordering need architect approval before a driver ABI is written.

Process `ru_maxrss` is separately measured per invocation in bytes on macOS. It includes runtime/allocator/code/OS effects and probe scaffolding, not just live tensors, and is not an SRAM budget. Exact known allocation sums exclude allocator, stack, tokenizer, libc/stdio, tracing and executable. Timing uses CLOCK_MONOTONIC immediately around each forward call and sums 32 or 16 durations; clock calls, instrumentation and the host scheduler limit interpretation. The reported cold process RSS high-water mark is read after all forwards and before exporting quantized weights; setup allocations remain live then. The probe retains both the original FP32 mapping and quantized weights to compare/reference them; a target image need not retain FP32 matrix weights.
